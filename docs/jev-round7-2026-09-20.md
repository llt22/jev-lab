## 1. 竞品叙事：Laya 对 Jev 的"prior art"挑战（已核实为不成立）

**来源**：[Hemant 长文](https://x.com/hemantXAI/status/2101575968905216261)（2026-09-20 15:35，35 赞）

Laya 关联作者（Hemant，openJev Verdict 作者）发布全面对比文章，核心声称：

> "Frontier labs are hyping non-autoregressive decision models as the newest breakthrough. In reality, this architecture was pioneered over a year ago by independent research."

**引用证据**：
- "Paper 1 (March 2025): Reinforcement Learning for Sequence Conversion Trajectories (arXiv:2503.23303)"
- "Paper 2 (September 2025): Schema-Based Decisions Guided by Reinforcement Learning (arXiv:2510.01237)"

**关键核实结果（直接抓 arXiv 全文）：**

| 声称 | 论文实际内容 | 结论 |
| --- | --- | --- |
| arXiv:2503.23303 = "相同架构一年前的论文" | SalesRLAgent：销售对话转化预测的 RL 方法（Azure OpenAI embeddings + 转化概率估计） | **不是**非自回归决策模型，是销售预测 |
| arXiv:2510.01237 = "相同架构" | Confidence-Aware Routing：LLM 幻觉缓解的置信度路由（对齐检测 + 预生成路由） | **不是**System One 决策架构，是幻觉缓解 |
| 作者身份 | 两篇论文作者 Nandakishor M = Laya 创始人本人 | 自证式 prior art，非独立第三方 |

**结论：Laya 阵营的"架构早已存在"声称，其引用的论文并不支持"相同架构"的说法。** 它混淆了"RL 训练做预测/路由"与"非自回归并行决策"两个概念。这属于竞品营销叙事，不应被视为 Prior Art 证据。生态层面反而印证了第六轮"护城河在数据配方与分发"的判断——**如果架构真那么简单，他们应该拿出架构级证据，而不是拿不相关的论文当挡箭牌。**

**与之矛盾的独立数据**：JevBench v1.2.2（第六轮核实）实测 Laya Calibration 62.5 / Intelligence 63.2，而 Jev 是 82.7 / 90.4。Hemant 声称的"ECE 0.081 vs 0.246"与 JevBench 的校准分存在明显落差，**在拿到原始评测数据前不可采信**。

## 2. 新基准：Nakajima carpooling——决策模型 vs LLM 的约束满足测试

**来源**：[Satoshi Nakajima](https://x.com/snakajima/status/2101568939830759550)（GraphAI 作者，2026-09-20 15:07）

这是第七轮**方法上最有意思**的新基准：拼车优化（carpooling optimization），不是为分类而设计，而是**约束满足 + 优化**型任务：

| 模型 | 准确率 | 延迟 | 成本 |
| --- | ---: | ---: | ---: |
| Claude Opus | 74.1% | 2.1s | $60 |
| GPT-5.6 Sol | 74.9% | 2.2s | $27 |
| Gemini 3.2 flash | 72.9% | 1.5s | $9 |
| **JEV** | **74.3%** | **0.13s** | **$0.34** |

**读法**：准确率全部挤在 74%±1（Sol 略高 0.6 个点，Jev 略高 Opus/Gemini），但成本差 **80–176 倍**、速度差 **12–16 倍**。这延续了六轮的结论：**质量相当、成本延迟碾压**，且首次在"优化型任务"（不是分类）上验证。限堵：尚未发布仓库和完整方法，为初审结果，不可直接引用为正式基准。

## 3. jev-recall：相关性召回——向量检索的结构性失效与 Jev 解法

**来源**：[ject-recall 帖](https://x.com/realfxw/status/2101578378356588888) + [仓库](https://github.com/samdotmak/jev-recall)（★13，MIT，已核实）

问题非常清楚：**Embedding 找"长得像"，不找"真正相关"**。示例：

> 用户："帮我为周六聚会订一份 Tartine 的杏仁挞。"
> 关键记忆："Leo 有严重的坚果过敏。"
> Embedding 只会捞烘焙/聚餐相关记忆，漏掉过敏警告。

**方法**：每条候选记忆转成一个校准 yes/no 问题，一次请求并行判断全部；用置信度阈值过滤（而非猜 Top-K）；无相关时返回空集。这比固定 Top-K 合理——校准概率允许"没有就返回空"。

**评测（238 条背景记忆、18 个反直觉关联测试）**：

| 方法 | 通过 | 单次成本 | 延迟 |
| --- | ---: | ---: | ---: |
| BM25/关键词 | 1/18 | — | — |
| OpenAI embedding (text-embedding-3-large) | 3/18 | — | — |
| Claude Sonnet 5（LLM re-ranker） | 17/18 | $0.020 | 7.6s |
| **Jev Recall** | **17/18** | **$0.00044** | **0.35s** |

**价值**：与 Sonnet 打平质量，成本 1/46、快 20 倍——"每轮必检"才变得可行。这直接把"相关性判断"从"昂贵重排"变成"廉价并行"。**同构于我们首轮"上下文过滤"与第三轮"可恢复压缩"方向，且给出了可复跑的评测协议。**

## 4. TypeAR：补齐开源复刻的数值字段缺口

**来源**：[TypeAR 仓库](https://github.com/TypeAR-AI/TypeAR)（★12，16 commits）

社区复刻一直有个明显缺口：Jev 契约的 Choice/Score/Noul 都是符号输出，**数值/整数字段怎么办**？TypeAR 给出了一条路线：给开源自回归模型加类型安全解码——

- integer/float 通过 tokenizer-native 约束解码直接输出数值
- 枚举用单 token 类别选择（几乎零输出 token 开销）
- 可选 thinking mode（per-field budget）再约束解码
- 前缀缓存让输入成本线性化

定位：不是"复刻 Jev 模型"，而是**让已有开源 LLM 具备 Jev 式接口**。与 KinasRemek 图谱中的"数值字段缺口"正好对应。

## 5. 开源实现选型图谱（KinasRemek）——"复刻怎么选"

**来源**：[KinasRemek](https://x.com/KinasRemek/status/2101577810301026687)（2026-09-20，波兰语）

这是目前看到**最实用的开源实现选型框架**，按使用场景分六档：

| 你的需求 | 选什么 | 理由 |
| --- | --- | --- |
| 本地即时"智能 if" | simple-jev / litjev | 零训练，精确 prompt 规格 |
| Apple Silicon 本地 | jevmlx / SemIf MLX | MLX 后端 |
| GPU 且要成绩 | SemIf | JevBench #3，无训练最佳实测 |
| 领域内质量 | bespokelabsai/nimble | contrastive curation + 2676 例 + LoRA r=16 + 1 epoch |
| 理解机制 | jaredpalmer/kev | block-causal mask + pointer head，1h45m 可训练 |
| 毫秒级窄域 | laya / jeff / deberta / Verdict（编码器路线） | Apache-2.0、CPU 可跑，**但自评与 JevBench 差距最大** |
| 数值/文本字段混合 schema | TypeAR | 约束解码 |
| 多模态 | DiffusionGemma | 唯一多模态路线，但未合并 PR |

三个关键提示：① 编码器路线的"自评"与独立基准的落差最大（呼应第六轮 Laya 的 62.5 vs 自评 90）；② nimble 的数据方法论（contrastive curation）是目前最严谨的；③ 生态已经从"复刻能不能"变成"按需选型"——**复刻潮的成熟度标志**。

### 6.2 Ian Nuttall：1.6k 书签分类（产品内）

[1.6k 书签 22 秒分类完](https://x.com/iannuttall/status/2101369410447437889)，比 GLM 4.7 Flash 快 155 倍、便宜 10 倍，用于 keep.md 向用户展示最有趣书签。

### 6.3 redp314：feed 优化器（few-shot 调优）

[每次调用 9 个概率](https://x.com/redp314/status/2100915304062710263) → HIDE/SKIM/KEEP；300 条未见书签 63% KEEP；150 条真实 For You 帖 10 秒 $0.015；16 条示例 few-shot、零训练。

### 6.4 Your Signal：Chrome 扩展信息流过滤（中文综述披露）

[xingpt 综述](https://x.com/xingpt/status/2101578499085504656)披露：Chrome 扩展，用户设兴趣+过滤偏好，Jev 判断 X 帖相关/是否实料/是否推广，按设置高亮淡化折叠隐藏（可撤销）。需自己的 API Key，文本远端处理。

## 10. 下一轮优先级

1. **复现 jev-recall 评测协议**（最易复现、与记忆/上下文方向最贴）：18 个反直觉关联测试 + Jev 概率找阈值，用我们自己的记忆数据（如 agent-control 工具调用）重跑。
2. **对照 Laya 声称的 ECE 0.081 与 JevBench 62.5 校准分**：Laya 权重开源、评测代码可跑，用同一批我们已标好的 eval 直接测原生 ECE——这是唯一能调和"3x 校准 vs JevBench 62.5"矛盾的方法。
3. **补 JevBench 的选项顺序鲁棒性**（继承第六轮）：用 yibie 的 24 排列方法验证我们的 support-routing/confidence 数据。
4. **用 Nakajima carpooling 的约束满足任务形态，补测我们未覆盖的"优化型"任务**（Search/Retrieval/Ranking 官方形态表之外的第五类）。
5. **盯 TypeAR/DiffusionGemma 后续**：数值字段处理是 Jev 契约的真实缺口，TypeAR 思路值得在中文工单场景试用。
6. 官方侧：免费期 9/25 结束后的留存/定价数据。
