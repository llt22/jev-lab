## 一处需要纠正的社区共识

第二轮之后，X 上开始流传一种说法：**"官方文档自己写了 Jev 不擅长多步推理，比如下棋。"** 这条被用来解释各种下棋、推理类测试的失败。

核对结论：**不成立。**

- 官方限制页是 [Model jaggedness: jev-1.13](https://docs.typesafe.ai/model-jaggedness/jev-1.13)，原文写的是 "It may struggle with tasks that require additional levels of indirection"、"A question about a property of a property or something that requires multiple hops of reasoning costs accuracy"、以及 "System Two tasks: more layers of indirections"。
- 抓取该页与 `docs.typesafe.ai/llms.txt` 全文索引后，**"chess" 一次都没有出现**。
- 也就是说，"下棋" 是社区自己挑的例子，不是官方的自我声明。传播这条说法的帖子（如 [@ai_with_gregor](https://x.com/ai_with_gregor/status/2100862957005738170)）把 "indirection" 简化成了 "下棋"。

这不是文字游戏。它决定了后续该怎么测：官方承认的失效面是**间接引用、双重否定、数值精度、日期比较、无关上下文腐化、自相矛盾的指令**，这些都可以构造出可自查答案的样例；而"下棋" 是一个未定义难度、未定义评测协议的自创任务，无法横向比较。

## 官方文档给出的硬约束（此前报告没有的系统整理）

| 项目 | 官方口径 | 来源 |
| --- | --- | --- |
| 当前版本 | `jev-1.13.0`；`jev-latest` 指向它；`jev-preview` 现无预览版 | [models](https://docs.typesafe.ai/models) |
| 价格 | 输入 $0.042 / M token（$42 / B token），**输出免费** | [models](https://docs.typesafe.ai/models) |
| 长度 | 每请求 64k token；其中 `state` 加最长问题约 32k | [models](https://docs.typesafe.ai/models) |
| 限流 | 250,000 token/s、1,200 请求/分钟，且**会动态调整、不另行通知** | [models](https://docs.typesafe.ai/models) |
| 输入类型 | 仅文本。字符串、JSON 对象或文本数组；无图像/音频/视频 | [state](https://docs.typesafe.ai/concepts/state) |
| Choice 上限 | **255 个选项** | [choice](https://docs.typesafe.ai/primitives/choice) |
| Score 级数 | 至少 2 级，最多 10 级 | [score](https://docs.typesafe.ai/primitives/score) |
| `confidence` 定义 | "由答案的概率分布推导"，是**分布集中程度**，官方明确 "does not guarantee that an individual answer is correct" | [confidence](https://docs.typesafe.ai/confidence) |
| 请求参数 | 只有 `state`、`model`、`questions`。**没有** temperature、max_tokens、思考预算 | [api](https://docs.typesafe.ai/api) |
| 流式 | 官方文档无 SSE / streaming 任何记载 | [api](https://docs.typesafe.ai/api) |
| 训练数据 | "Jev is not trained on customer requests or responses." | [models](https://docs.typesafe.ai/models) |

两点需要提醒：

1. **官方文档内部不一致。** [primitives](https://docs.typesafe.ai/primitives) 说预算 "around 32,000 tokens"，[models](https://docs.typesafe.ai/models) 说 "64k tokens per request"。做容量规划时不能只挑一个数字。
2. **"零幻觉" 的真实含义。** 官方博客原句是 "While Jev gives up string generation, it's optimized for structured outputs and can't hallucinate"，配合 "Schema matching is guaranteed"。它保证的是**输出永远是合法枚举值**，不是"选的那个答案一定对"。社区帖子（如 [@bshmacro](https://x.com/bshmacro/status/2100866405151158338)）自行做了这条纠偏，方向与官方一致。

这也解释了本仓库第二轮流式监督实验的处境：官方 API 既不提供 `reasoning`，也没有思考预算参数，第二轮能观察到的 SSE 来自第三方网关而非 Jev。**"Jev 流式思考监督" 严格来说是网关层实验**，这一点应在引用时说明。

## 官方 SDK、Agent Skill 与网关

| 项目 | 核实结果 |
| --- | --- |
| Python SDK | PyPI `typesafe-sdk` **0.6.0**，发布于 2026-09-15；`client.system_one(state=..., questions={...})`，响应有 `.nouls` / `.choices` / `.scores` |
| JS SDK | npm `@typesafe-ai/sdk` **0.6.0**，发布于 2026-09-15；`client.systemOne({state, questions})`，零运行时依赖 |
| 官方 Skill | [typesafe-ai/skills](https://github.com/typesafe-ai/skills) ★146，MIT，v0.5.7；**只有 SKILL.md，没有可执行代码** |
| Skill 内容 | 把 `docs.typesafe.ai/llms.txt` 当唯一事实来源；规则/计算/查表/副作用留给代码，只把语义判断交给模型；每个问题一个窄判断 |
| Python 适配器 | `typesafe-ai/system-one-adapter-python` ★96，用 TypeSafeClient 包住 OpenAI/Anthropic |

三个容易踩的坑：

1. **`npx skills` 不是 TypeSafe 的工具。** 官方文档给的 `npx skills add typesafe-ai/skills --skill typesafe-ai` 里，`skills` 这个 CLI 来自 **vercel-labs/skills**（npm 包 `skills` 1.7.0，第三方）。TypeSafe 自己没有发布任何 CLI（`@typesafe-ai/cli`、`@typesafe-ai/skills` 均 404）。
2. **npm 上有同名假包。** 存在一个无仓库字段、版本 0.0.0 的 `typesafe-sdk`；官方 JS 包是带 scope 的 `@typesafe-ai/sdk`。
3. **文档提到但仓库里没有的东西。** 官方说明让复制 `skills/typesafe-ai` 目录"包含它的 reference files"，而该仓库只有 7 个文件，不存在任何 reference files。

网关方面，本轮新增一条此前未记录的：**Netlify AI Gateway（2026-09-17 更新日志）**。加上 Vercel、Cloudflare、OpenRouter，第三方入口至少四条。但要注意：**官方文档从头到尾没有提过任何网关**，这些都属于第三方页面；且 Cloudflare 目录把 Jev 标成 "Text Generation"，与官方 "不生成文本" 的定位直接冲突，说明目录分类并不可靠。

## 本轮新做的实测：置信度能否当作升级闸门

社区这一轮最热的问题，是 [@krishras23](https://x.com/krishras23/status/2100762524149047770) 提出的那个：**能不能用 Jev 做便宜的快速首过，只在它不确定时付钱给强模型。** 这正好是本项目第一阶段留下的未验证项，于是构造了一个可直接复跑的探针。

### 设计

- 数据集 [`evals/confidence-escalation-v1.json`](../evals/confidence-escalation-v1.json)：36 条，6 组各 6 条，分组直接对应官方承认的失效面——`clear`（基线）、`negation`（双重否定）、`indirection`（属性之属性、多跳）、`numeric`（算术、计数、日期差）、`context_rot`（同一事实，一段干净一段塞满无关材料）、`contradictory`（规则冲突、状态自相矛盾、诱导指令）。
- **每条答案都能在不调用任何模型的情况下核对**，所以测的是事实而不是"另一个模型的看法"。
- 升级决定由确定性代码从概率分布算出，Jev 不参与决定自己是否升级。
- 脚本 [`scripts/evaluate_confidence_escalation.py`](../scripts/evaluate_confidence_escalation.py)，三轮共 108 次决策 + 18 次分解请求，0 次接口错误，总输入 64,998 token（按官方价格约 $0.0027）。

这个方法设计本身立刻产生了一次价值：第一版有两条样例的**我自己标错了**——8/12 = 66.7% 四舍五入应为 67 而不是 66，另有一条日期题措辞有歧义。因为答案可独立核对，这两处在重跑时被暴露并修正。第一版结果（91.7%）已作废。

### 结果

三轮结果：

| 运行 | 准确率 | 延迟 P50 |
| --- | ---: | ---: |
| 第 1 轮 | 97.2% | 1400 ms |
| 第 2 轮 | 94.4% | 1380 ms |
| 第 3 轮 | 94.4% | 1409 ms |

**负结果一：官方自认的失效面在这个难度下没有复现。** `negation`、`indirection`、`numeric`、`context_rot` 四组都是 6/6 全对，三轮稳定。这不是"Jev 没有这些弱点"，而是**这些弱点需要更难的实例才会出现**：本探针的双重否定是单句、间接引用只有 2–3 跳、算术是整数、加料版的无关内容只有约 300 字。官方说的是 "additional levels of indirection" 与 "context rot"，我构造的难度不够。

**负结果二：无关上下文没有造成退化。** 三对"同事实、不同长度"的对照全部两侧答对，闸门值只从 0.970 掉到 0.960–0.970。官方警告的 context rot 在 300 字级别的干扰下没有出现，需要真正长状态才能测。

**唯一稳定失败的是"规则冲突"。** `con-1` 给出两条互相冲突的分类规则（"按客户主诉分类" vs "客户自填标签优先"），Jev 三轮都选了客户自填标签，而按业务定义正确答案是主诉。关键在这里：

| 条目 | 三轮预测 | 三轮 `confidence` | 三轮 top-1 概率 |
| --- | --- | --- | --- |
| `con-1` | 全错（network） | **0.160 / 0.090 / 0.040** | 0.580 / 0.540 / 0.520 |

**官方 `confidence` 比 top-1 概率灵敏得多**：top-1 概率始终在 0.58 左右，看上去像"过半支持"，而 `confidence` 只有 0.04–0.16，一眼就是"别信我"。这是本轮最有实用价值的一条机制发现：**如果要用闸门，用 `confidence`，不要用 argmax 概率。**

**唯一一次决策翻转正好落在日期题上。** `num-6`（2026 年 2 月 + 3 月共几天）第 1 轮答 59（正确），第 2、3 轮答 58。这正是官方写的 "reads dates as text, not as ordered quantities"。108 次决策里只翻转 1 次，决策一致率 99.1%，平均闸门波动 0.0125。

**分解对照：把同一个问题拆成 32 个窄 Noul，比问一个 Score 更稳。** 同一批数字题，用 32 个"答案是否等于 X"的 Noul 取 argmax：三轮全部 6/6 正确、正确答案平均排名 1.0、命中概率 0.92–1.00。而同一个 `dec-6` 用 Score 问时三轮里错了两次。

| 题 | Score 三轮判定 | 32-Noul argmax 三轮 |
| --- | --- | --- |
| `dec-6`（2 月+3 月天数） | 59 / 58 / 58 | ✅ / ✅ / ✅ |
| 其余 5 题 | 全对 | ✅ / ✅ / ✅ |

这和官方自己的建议一致（把计算和查表留在代码里，只把判断交给模型），但它给出了一个更具体的操作规则：**数值和日期类判断应当默认分解成窄 Noul + 代码取值，而不是交给 Score。**

### 合并三轮的闸门扫描

| 阈值 | 自动通过率 | 自动通过准确率 | 升级数 | 升级中确为错误 | 错误捕获率 | 漏放错误 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0.50 | 97.2% | 98.1% | 3 | 100% | 60% | 2 |
| 0.60 | 91.7% | 100.0% | 9 | 56% | 100% | 0 |
| 0.70 | 91.7% | 100.0% | 9 | 56% | 100% | 0 |
| 0.80 | 90.7% | 100.0% | 10 | 50% | 100% | 0 |
| 0.90 | 81.5% | 100.0% | 20 | 25% | 100% | 0 |

读法：阈值取 0.6–0.7 时，91.7% 的决策可以自动放行且平均全对，5 个错误全部被送进升级队列，代价是 8.3% 的样本要付第二次钱。阈值降到 0.5 反而会漏放 2 个（都是 `num-6` 那两轮，闸门 0.55）。

**必须说明的限制：三轮是同一批样本的重复计数，不是独立样本；总共只有 5 个错误，"错误捕获率 100%" 的置信区间极宽。** 这条结论目前只能支持"机制成立、方向正确"，不能支持任何生产阈值。原始数据、每轮明细与稳定性对比见：

## 本轮之后的判断变化

1. **"Jev 不能做多步推理"要降级。** 那是社区对官方 "indirection" 的误读，官方从没提过下棋；而且在本轮探针里，双重否定、2–3 跳间接引用、整数算术都没有失败。真正稳定失败的是**互相冲突的指令**，以及**日期类判断的翻转**。
2. **置信度作为升级闸门，从"值得测"变成"有初步机制证据"。** 唯一稳定的错误带着 0.04–0.16 的 `confidence`；取 0.6–0.7 阈值可放行九成决策且不放过任何错误。但错误总数只有 5 个，仍不足以定阈值。
3. **`confidence` 应优先于 argmax 概率作为闸门信号。** 在失败样例上两者差了一个量级（0.16 对 0.58）。
4. **数值与日期判断默认走分解。** 32 个窄 Noul + 代码取 argmax，比一个 Score 稳，且成本仍极低。
5. **生态索引不可轻信。** 最高星的仓库可以不在最有名的 awesome 列表里；`npx skills` 是第三方 CLI；npm 有同名假包；同一项目在不同索引里 star 数对不上。引用必须回到仓库和 API。
6. **生产接入开始出现，但都在低风险位。** 目前看到的最稳形态是 Orus 的"动作前否决 + 自然语言条件 + 模拟盘"。仍未看到任何高风险自动执行被允许。
7. **官方文档本身也有质量缺口**（32k 与 64k 自相矛盾、"reference files" 不存在），第三方目录则把不生成文本的模型标成 "Text Generation"。对官方数字同样要交叉验证。

## 下一轮优先级

1. **把失效面探针加难。** 当前难度不足，需要：真正的 4–6 跳间接引用、带冲突证据的长状态（数千字）、需要多步计算的日期与时区问题、中文与中英混合工单（官方声明英语为主，本仓库从未测过）。
2. **真的跑一次升级级联。** 本实验只测了闸门能捕获多少错误，没有实际调用强模型。下一步应接入现有网关，比较"全程强模型" vs "Jev 首过 + 不确定时升级"的总成本、总成功率和升级率——这正是下棋作者提出的问题。
3. **用官方 SDK 替换手写 HTTP。** 四个评测脚本目前都自己拼 `urllib` 请求；官方 Python SDK 已到 0.6.0，应当迁移以降低维护成本，并固定 `jev-1.13.0`。
4. **把 `confidence` 与 top-1 概率的差异做成常规指标。** 两者在失败样例上的分离度比准确率更能反映"能不能自动放行"。
5. **监控版本漂移。** 官方声明限流动态调整；应记录每次运行的实际模型 ID 与价格口径，避免跨版本比较。
