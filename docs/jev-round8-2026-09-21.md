## 一句话结论

**Jev 生命周期进入新阶段：官方全面开放（无 waitlist + $5 额度）伴随生态的"验证潮"。** 本轮出现三个高质量独立证据：**西班牙语预注册审计**（首次量化的非英语成本）、**DevelopersIO 假设检验**（否证"Jev 快只因不生成文本"）、**JevBench v1.2.7 榜单修正**（代理层降级，Jev 重回榜首）。同时 Google 官方开始宣传 DiffusionGemma-as-Jev，**竞争从社区走向主流实验室**。治理层面出现迄今最完整的框架——"评估机/判定机"与数据主权批判。

## 2. 西班牙语审计：首个预注册、可复现的非英语量化

**来源**：[Marcos Martinez（Fligoo）](https://x.com/ingmmartinez/status/2101848155679535326) + [仓库 jev-acento](https://github.com/marcosmartinez/jev-acento)（MIT，CLI 可复跑）

**这是本轮方法学最强的独立审计**，也是对我们"中文/非英语缺口"（第三轮起反复标记）的范式级参照：

**设计**：19,200 次调用、3,200 个人工标注配对项、4 个数据集（XNLI/PAWS-X/MASSIVE/Belebele）、$0.58、jev-1.13.0 pin、**预注册**（PREREG.sha256 冻结）、三臂配对（A 英/英、B 西/英、C 西/西）、字节相同校验、噪声地板 ECE、paired bootstrap、三个判定闸门（INESTABLE/AMBIGUO 可发布）。

**四个结果：**

| 发现 | 数据 |
| --- | --- |
| 西语文本扣 accuracy | XNLI −6.4pp、PAWS-X −6.2pp、MASSIVE −3.7pp、Belebele −3.0pp（全部显著） |
| 困难任务校准破裂 | XNLI ECE 0.057→0.101、PAWS-X 0.033→0.078；AURC XNLI 0.053→0.101 |
| 西语 questions 无益 | 3 个 null、1 个 ambiguous；应保留英语 instructions/criteria |
| token 溢价可忽略 | 文本多耗 17–38%，但完整调用只增 0.1–8.2% |

**操作级结论（最重要）**：以自动阈值 0.9 运行，西语的覆盖率掉 2–9pp、自动化部分错误率升 **1.3–1.9 倍**——**"在英语上校准好的阈值不能移植到其他语言"**。这与我们第三轮"阈值必须在自己数据上校准"的结论直接互相印证，且给出了完整方法模板。

**附带三个 API 机制细节**（直接修正我们可能的实现假设）：
1. **Noul 不返回 confidence**（Choice 返回）——PAWS-X 类阈值计算只能从 p_max 出
2. **confidence 与 p_max 不是同一函数**：俄语审计的 (k·p_max−1)/(k−1) 关系残差 ≤0.02（截断而非四舍五入）
3. **choice 与 probabilities 的 argmax 偶发不一致**：19,200 次中 8 次（两个小数位平局）——实现应统一用 argmax 而非直接取 choice 字段

**对照俄罗斯审计**：俄语 XNLI accuracy 掉 11.0pp、ECE 0.032→0.096、token 3 倍；西语约为其一半幅度的拉丁文字损失。官方"English is primary, others handled but not equally well"首次有了分语言的量化刻度。

## 3. DevelopersIO 假设检验：否证"Jev 快只因不生成文本"

**来源**：[Classmethod 文章](https://dev.classmethod.jp/articles/jev-vs-gemini-flash-cross-match/)（けーま，2026-09-21）

**这是对本轮 Laya 阵营"1,500ms latency tax"叙事的直接实验反驳**：

- **质疑**："Jev 快只是因为它不生成文本？那把 LLM 输出压到几个 token 也应该一样快。"
- **对照**：同样 107 案例、同样 questions（import Jev 脚本）、Gemini 3.8 Flash structured output 压到 2 个数字、thinking=low（minimum 不可用）、keepalive（对 Gemini 有利）
- **结果**：Jev 中位 **709ms** vs Gemini **1635ms**（2.3 倍慢）；Gemini thinking=0 的 57 件仍 **1616ms**——"输出生成量不是 Jev 快的原因，TTFT 是"
- **概率对比（最有价值）**：Gemini 概率全部贴在 0/1——exact 107/107 全 0.0/1.0，semantic 64 件 1.0 + 29 件 0.0，迷茫仅 1 件；**Gemini 的 5 个错判输出概率全为 1.0/1.0/0.95/0.0/0.2——自信地错，阈值门控完全失效**。Jev 在矛盾案例给 0.6–0.7 中间值可走人审
- **成本**：$0.0023 vs $0.0429（~19 倍），尽管 Gemini 输入 token 只有 Jev 一半（246 vs 509）
- **作者结论**："概率作为门控阈值时，Jev 的内部计算概率远比 LLM 的文本自我申报值实用"

这个实验直接回应了我们"置信度能不能用于闸门"的核心问题，且是从另一个角度（死对头假设）验证了 Jev 概率的实操价值。

## 5. Google 官方入场：DiffusionGemma-as-Jev

**来源**：[Google Gemma 官方](https://x.com/googlegemma/status/2101069861598482817) + [Matt Mastracci](https://x.com/mmastrac)（vLLM PR #57250 作者）

- Google 官方账号宣传"DiffusionGemma as Jev"：画布扩散单步去噪（DGX Spark ~0.2s）、完整双向注意力、多模态（Gemma 4 视觉）
- Matt 评估（69.2 万浏览）："Jev 更快？不（API vs DGX Spark）。Jev 更聪明？不（大致持平）"

- 限制：PR 未合并、prototype

**这是竞争走向主流实验室的标志**：不只是开源社区复刻，而是 Google 官方架构路线（扩散 vs 编码器 vs 自回归）开始对标 Jev 契约。与第六轮 JevBench"2 天 6 克隆"、"架构不是壁垒"的判断持续吻合，且多模态是 Jev 当前明确没有的维度。

## 6. 新项目：jevshield——Agent 安全门

**来源**：[jevshield](https://github.com/lgy1027/jevshield)（官方开放公告评论区发现）

- **Sub-100ms Agent 安全断路器**：破坏性操作（删库/高危 Shell）执行前拦截，按置信度阻断或降级
- **双层验证矩阵**：Severity Tier（Choice）× Irreversibility（Noul）交叉验证，消除单信号误报
- 零配置本地启发式回退、LangChain 集成、Apache-2.0 v0.1.1
- 提示注入防护：工具 docstring/参数包装为 "data not instructions" 前言

与 LangChain AutoModeMiddleware、Jev-cu policy.mjs 同范式——"动作前否决位 + 代码兜底"家族再添新成员。这是官方开放后第一个在公告评论区自然涌现的生产级安全组件。

## 7. 治理框架：评估机/判定机与数据主权批判

**来源**：[Exapolicy zenn 文章](https://zenn.dev/exapolicy/articles/06c15d967e4245)（プロマネ武蔵，2026-09-21）

第七轮关注技术，这轮出现了**迄今最完整的治理视角**：

**"Jev 不解释为什么"是设计而非缺陷**——LLM 事后编造的说明比没有更不可靠（作者先前的文章已论证）。

**三层结构**：
```text
评估（AI）  → 概率/分数/分类
判定（Policy）→ 用户事先写的基准与阈值（通/停/人）
判断（Human） → 判定机转给人看的最后案例
```

**三个外置说明责任点**：① 事前（问的设计：选项/轴/阈值）② 事后（判断的记录：输入→选项→概率→阈值→动作）③ 判断点（人介入条件）。**三者齐了，"为什么这条被这样处理"不靠模型也能回答。**

**关键批判（数据主权）**：Jev 是云端 API——"3 个外置只有在评估**本地**运行时才真正成立"。分流场景里，邮件/工单/未公开案件名**为了分流，把分流对象本身整段送出了**；速快价低反而让流出量变大。结论："该问的不是有多快，而是评估在哪里跑。"

**与 jev-lab 的互补**：我们第三轮以来的"输入输出全部落盘 + 阈值即策略 + 可恢复设计"在技术层面吻合①③；但数据主权问题——评估是否必须上云——是我们此前未系统标记的维度。对本仓库的启示：**客服工单（含 PII）若走官方云 API，必须先确认 DPA/ZDR 条款**（第四轮已记录 Enterprise ZDR 存在）。

## 9. 对本仓库结论的对照

| 既有结论 | 第八轮证据 | 状态 |
| --- | --- | --- |
| 阈值必须在自数据校准 / 置信度排序而非概率 | 西语审计：英语阈不可移植（错 1.3-1.9x）；DevelopersIO：LLM 概率贴 0/1 无法门控 | **强化**——两个独立实验从不同角度支持 |
| confidence 优先于 argmax（第三轮） | 西班牙语审计：#3 choice 与 argmax 偶发不一致（8/19,200） | 强化：实现应统一取 argmax |
| 中文精度未验证（第三轮） | 西语审计给出"非英语成本"完整方法模板（预注册+配对+可复现） | **方法模板到位**——可在中文上复刻 |
| 延迟 1.5s 主要是连接开销（第四轮） | DevelopersIO：Jev 709ms 中位（含日本网络）；西语 p50 327-482ms | 一致 |
| "概率不能用"结论细化 | DevelopersIO 证明 Jev 概率是内部计算值（0.6-0.7 矛盾信号），LLM 是文本申报值（0/1 贴死） | **新增机制理解**：Jev 概率的门控价值来源 |
| 护城河在分发/数据配方（第四轮） | Google 官方入场 DiffusionGemma；kev 0.6B 进 67 档 | 强化：主流实验室已跟进 |
| 服务可用性良好 | 25.8k 次 1 次 503（biscuit）等更早数据仍有效 | 不变 |
| 数据主权未系统审查 | Exapolicy：云端评估=分流对象整段外送，速快价低让流出更大 | **新增维度**：PII 场景须先确认 DPA/ZDR |

## 10. 下一轮优先级

1. **用 jev-acento 方法模板复刻中文审计**：同一设计（预注册、配对三臂、4 数据集、噪声地板 ECE）跑中文 vs 英语——这是第三轮遗留"中文无有效证据"的标准化解法，且全套工具已开源。
2. **修正我们脚本的 choice 取值逻辑**：统一用 probabilities 的 argmax（西语审计发现 choice 字段偶发不一致）——一个低成本高价值的代码修正。
3. **核对官方开放后的定价/条款**：$5 额度、console 开放后确认官方 API 与 Vercel Gateway 的 DPA/ZDR 差异，为客服/PII 场景选通道。

5. **复验 DevelopersIO 的"概率贴 0/1"对照**：用我们的 eval 集对比 Jev 与一个通用 LLM 在相同问题上的概率分布形态——直接检验"LLM 概率不可门控"。
